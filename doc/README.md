## 想定している作業の流れ

細かい担当分担は未確認だが、準備しておくなら以下の流れ。

1. **対象確認**：アカウント、リージョン、環境、リソースID、現行・更新先バージョンを照合する。
2. **現状確認**：冗長構成、接続先、パラメータ、監視、CloudFormationとの対応を記録する。
3. **更新条件の確認**：更新可能な経路、リリースノート、互換性、関連設定を調べる。
4. **手順・事前準備**：既存手順を確認し、バックアップ、承認、動作確認、中止・復旧の条件をそろえる。
5. **開発・テスト環境で更新**：コンソールから実施し、時間、状態遷移、接続への影響を記録する。必要なら手順を修正する。
6. **本番更新**：レビュー・承認済みの手順で作業し、証跡と進捗を残す。
7. **更新後確認**：バージョン、接続、データの読み書き、監視、アプリ動作を確認する。
8. **CloudFormationの整合**：実環境とテンプレート・パラメータを比較し、現場の手順で修正・反映する。
9. **完了報告**：結果、残課題、未確認事項をまとめ、台帳や手順書を更新する。

## CloudFormationで押さえておくところ

### コードを読む練習

- `Parameters`、`Resources`、`Outputs`、`Mappings`、`Conditions`。
- `!Ref`、`!GetAtt`、`!Sub`。
- 論理IDと物理ID。テンプレートのどの記述が実際のどのリソースか。
- `AWS::RDS::DBInstance`と`AWS::RDS::DBCluster`。
- `AWS::ElastiCache::ReplicationGroup`。必要なら`AWS::ElastiCache::CacheCluster`も確認。
- `EngineVersion`の指定場所。直接書かれているのか、パラメータやマッピングから渡しているのか。
- `DeletionPolicy`、`UpdateReplacePolicy`と、プロパティごとの更新時の影響。
- ネストされたスタックや、別スタックを参照している場合の依存関係。

現場のコードをまだ見ていないので、まずは上記を読めるようにしておく。

### コンソール変更後の整合

コンソールで変更しても、テンプレートが自動で書き換わるわけではない。比較するのは次の3つ。

1. 実際のAWSリソースの設定。
2. CloudFormationに保存されているテンプレートとパラメータ。
3. 次回の反映に使う管理元のコード・パラメータファイル。

どこに正本があり、誰が修正・レビュー・反映するのかを確認する。

ドリフト検出では、対応していないリソースやプロパティ、明示的に指定していない値などは確認できない。実際のバージョンや設定も照合する。

変更セットでは、意図した変更だけか、置換・削除・余計な更新がないかを見る。作成しただけでは反映されず、実行の成功が保証されるわけでもない。古い設定へ戻したり、無関係な差分を反映したりしないよう、変更セットの作成方式とドリフトの扱いも確認する。

バージョンを合わせるだけでも、再起動やダウングレードなどの扱いは対象サービスの仕様と検証結果で判断する。

参考：[ドリフト検出](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-stack-drift.html)／[変更セット](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html)

## 自宅でやっておきたいこと

書籍は最初から進めて、AWS全体のつながりを理解する。そのうえで、案件で必要になりそうな作業を練習する。以下はこれから取り組む候補。

### まず全体構成を確認

VPC、サブネット、ルート、SG、EC2、ALB、RDSのつながりを、コンソールと構成図で確認する。通信できない場合に、どこから調べるかを考えられるようにしたい。

リソースの作成完了、接続成功、アプリの動作確認は別々に記録する。

### CloudFormationとGit

小さな構成で、テンプレートと実リソースの対応を確認する。パラメータ変更、変更セット、イベント、ドリフト検出も試す。最初のコンソール変更は、ドリフト検出に対応する影響の小さい設定で行う。

VS Codeで編集し、Gitはコマンドの意味を確認しながら使う。

```text
git status
git diff
git add ファイル名
git diff --staged
git commit -m "変更内容"
git push
```

ブランチ作成やレビューは、この流れに慣れてから練習する。

### RDSを更新して、CloudFormationと合わせる

まずMySQLかMariaDBのどちらかで一巡する。もう一方は違いを確認する。

1. 利用可能なバージョンと更新経路を調べ、学習用の小規模なRDSをCloudFormationで作る。
2. テストデータを入れ、バージョン、接続、読み書きを記録する。
3. スナップショットを取得し、復元時に確認する項目を整理する。
4. コンソールから更新する。適用タイミング、状態遷移、接続切れ、復帰までの時間を確認する。
5. 更新後のバージョン、データ、接続を確認する。
6. 実環境とテンプレート・パラメータを比較する。
7. 修正差分と変更セットを確認し、整合を取るところまで試す。
8. 結果をメモして、不要なリソースを削除する。

現場と同じ旧バージョンを新規作成できない場合は、再現できない条件をメモしておく。

### AuroraとRedis

AuroraはWriter／Readerと各エンドポイント、クラスター・インスタンスの関係を確認する。通常のRDSと同じ手順でよいと思い込まないようにする。

RedisはテストキーとTTLを用意し、更新前後の接続とデータを確認する。クラスターモードやレプリカ構成、フェイルオーバー、クライアントの再接続も理解しておきたい。現場でキャッシュを何に使っているかも確認が必要。

構成やバージョンによる違いは公式資料で確認する。

参考：[Aurora MySQLの更新](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Updates.html)／[ElastiCacheの更新時の注意点](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/VersionManagement-upgrade-considerations.html)

費用を見て、サービスを一つずつ短時間で試す。冗長構成を試す場合は必要な台数を用意し、単一ノードの結果と区別する。

### 復旧と報告

RDSのスナップショットから復元して、データと接続先を確認する。復元では新しいDBインスタンスが作られるので、接続先の切替と更新後データの扱いも考える。AuroraとRedisは、それぞれに合った復旧方法を確認する。

参考：[RDSスナップショットからの復元](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RestoreFromSnapshot.html)

開始、途中経過、エラー、完了を簡潔に説明する練習もしておく。DBが利用可能になったことと、アプリの動作が確認できたことは分けて報告する。
