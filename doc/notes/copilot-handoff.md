# Copilotへの引き継ぎメモ

## このメモについて

AWSのデータベース更新作業に向けて、自宅で学習した内容と、これから手伝ってほしいことをまとめた。
公開リポジトリに置くため、会社名、作業日、台数、環境を特定できる情報は省いている。
対象名や社内の手順は、会社で認められた場所に保存する手元のコピーに追記する。
このメモ自体は、作業承認済みの手順書ではない。

## 今の担当と優先したいこと

- RDSのマイナーアップデートを担当する。更新方式はインプレースと聞いている。
- CloudFormationを使い、AWSのWebコンソールから更新する。
- リーダと画面共有しながら、作業者と確認者の二人体制でリモート作業する。
- 過去の手順書がある。まずはそれを参考に、自分が担当する各作業日の手順書を作ることが最優先。
- 自分の作業より前に、リーダが更新作業を実施する。その際は私が確認者として手順と結果を確認する。
- その後の自分の担当日は、私が操作し、リーダに確認してもらう予定。

以前は「コンソールで直接更新した後にCloudFormationを合わせる」と理解していたが、その後の説明で「CloudFormationから更新する」と分かった。現在は後者を前提に準備する。

## ソース管理について分かっていること

- 実際の環境ではCodeCommitを利用している。
- 自分の対象の一つは、SVN（Subversion）で管理されているJSONテンプレートを使う。
- YAMLとJSONの両方がある。対象ごとのリポジトリ、ファイル、ブランチの対応は確認が必要。
- 過去にGitHubの話も出たが、今回のレビュー先がGitHubだとは決めつけない。

CodeCommitはGitを使うが、認証方法やレビューの画面、ブランチ運用は現場のルールに従う。SVNは別の手順として扱う。SVNのcommitはサーバへの反映になるので、Gitのローカルcommitと混同しない。

## 自分が学習済みの範囲

- MacとWindowsのVS CodeのターミナルでGitとAWS CLIを使用した。
- Gitのstatus、diff、add、commit、push、pullを練習した。
- 自宅のCloudFormation環境では、VPC、サブネット、Internet GatewayとVPCへの接続を作成した。
- テンプレートの検証、変更セットの作成、差分確認、実行、完了待ち、リソース確認を練習した。
- YAMLのインデントや`!Ref`などを学習中。

CodeCommit・SVNを使った現場のレビュー／マージ運用と、RDSのバージョンアップは、まだ実務経験がない。
「リクエストを出す」「ブランチを切る」「作業前にマージする」という説明を、操作と結び付けて理解したい。

## 最初に現場で確認すること

| 確認項目 | 確認したい内容 |
| --- | --- |
| 取得元 | CodeCommit／SVNのどのリポジトリ、どのファイルを使うか |
| 修正場所 | 元になるブランチと作業ブランチ。SVNの場合は対象URLとブランチ運用 |
| 確認依頼 | 「リクエスト」が何を指すか、どの画面で作り、誰にレビューを頼むか |
| マージ | 取り込み元、取り込み先、実施者、タイミング。「作業前」とはどの作業の前か |
| 反映する版 | 承認されたコミット／SVNリビジョン、テンプレート、パラメータと変更セットの対応 |
| 自動処理 | pushやマージをすると、自動デプロイなどが動くか |

確認するまでは、元ブランチがmain、私がマージ担当、マージ後に反映する、といった運用を仮定しない。

## 確認後に進めたい流れ

1. 過去の手順書を読み、対象ごとの差分を整理する。エンジン、更新前後のバージョン、構成、パラメータグループなど、不明な項目は未確認として残す。
2. 指定された取得元と版から作業を始める。CodeCommitとSVNはそれぞれ現場の手順に従い、作業場所と未反映の変更を確認する。
3. 必要なテンプレート修正と手順書の作成を行う。JSON／YAMLの形式を維持し、無関係な整形や変更を混ぜない。
4. 構文と差分を確認し、決められた方法でレビューを依頼する。コードだけでなく、事前確認・操作・事後確認・異常時対応も確認してもらう。
5. 決められた担当者が、決められたタイミングでマージする。承認された版を記録し、AWSへ反映するファイルと一致させる。
6. リーダの作業日に、確認者として確認点と判断基準を覚える。自分の対象と構成が違う部分は分けて記録し、手順書を補正する。
7. 自分の作業日は、対象と操作を読み合わせ、リーダの確認を受けて実施する。結果と証跡を残す。

上記は準備の流れ。現場の承認手順が分かれば、それに合わせて順番を修正する。

## 手順書に必要な確認項目

- 対象のAWSアカウント、リージョン、スタック、DBを取り違えないための照合。
- 現在と更新先のエンジンバージョン、対応する更新経路、構成と関連設定。
- 作業時間、停止や接続断の見込み、アプリ側の確認担当。
- バックアップの確認、復旧方法、復旧の判断者と所要時間の見込み。
- 使用するテンプレートのコミット／リビジョンとパラメータ。
- 変更セットで確認する対象、変更内容、置換や想定外の変更の有無。
- 各操作の期待結果、確認者の確認タイミング、異常時に止める条件。
- 更新後のスタック状態、DBの実際のバージョン・状態・保留中の変更、アプリ側の動作確認。
- 保存する証跡と完了報告先。

CloudFormationの完了だけでアプリの正常性まで確認できたことにはしない。また、切り戻しを単純な旧バージョンへの変更として書かず、対象に応じた復旧方法を確認する。

## まだ意味が確定していない説明

- 「CloudFormationの更新後にTerraformのstateとの差分を見る」と聞いた。実際に使うツール・コマンド、管理範囲、比較する目的は未確認。CloudFormationのドリフト検出と同じ意味だとは決めつけない。
- Redisについて「フェイルオーバーのためにオートスケーリングを設定する」という説明も聞いたが、正確な構成変更は未確認。今回のDB手順書作成とは分けて確認する。

## Copilotにお願いしたい進め方

私は初めての対応なので、まず上の確認事項と過去の手順書をもとに、不足情報を整理してほしい。
一度に大量のコマンドを出すより、一つずつ目的を説明し、結果を確認してから次に進めたい。

- 確定した事実、推測、未確認事項を分ける。
- コマンドは実行場所、目的、変更の有無、期待される結果を説明する。
- リポジトリ名、ブランチ名、AWSの対象名、バージョン番号を推測して埋めない。
- リクエストやマージを説明するときは、「どこからどこへ」「誰が」「いつ」を具体的に示す。
- テンプレートは最小限の差分にし、変更理由を説明する。
- 本番作業の承認や判断はリーダの確認に従う。AIの回答だけで実行可否を判断しない。
- 社内資料は社内のAI利用ルールに従って扱う。社内情報をこの公開リポジトリへ書き戻さない。

最初は「対象ごとの取得元・修正場所・レビュー方法・マージ・反映する版」の確認結果を私に聞き、それをもとに手順書作成を手伝ってほしい。
