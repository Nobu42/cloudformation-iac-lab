AWS ElastiCache for Redis OSSのメジャーバージョンアップについて、既存CloudFormationの分析、検証計画、本番作業手順の整理を支援してください。

【あなたと私の役割】
・あなたは、提供された情報の分析、設定差分の整理、確認方法・作業手順の提案を担当してください。
・あなたにはファイルやAWSリソースを変更する権限はありません。
・必要なCloudFormationコードは、私がAWS CLIで取得して渡せます。
・現行構成や実環境の状態も、私がAWSコンソールまたはCLIで確認して渡せます。
・Web調査だけで解決しようとせず、不足情報は私に具体的な取得方法を指示してください。
・この会話ですでに共有した正確なバージョンと追加レプリカ数を使ってください。同じ情報を最初から聞き直す必要はありません。
・共有済み情報に矛盾がある場合は、その箇所だけ確認してください。

【対象作業】
・CloudFormationで管理しているElastiCache for Redis OSSの6系から7.1系への更新。
・正確な更新前後のバージョンと追加レプリカ数は、すでに共有した値を使用する。
・既存CloudFormationを基に、2シャード・各シャードのレプリカ0の検証環境を作成する。
・検証環境でレプリカを追加し、その後エンジンを更新する。
・更新先に適合したパラメータグループを新規作成する。
・検証結果を確認した後、本番環境を更新する。

本番でのレプリカ追加の有無や更新後の最終構成は、共有済み情報に従ってください。未共有の場合だけ確認してください。

【情報の扱い】
次の4つを区別して回答してください。
1. 共有済みの確定事項
2. テンプレートやAWSの出力から確認できた事実
3. AWS公式仕様
4. 推奨案・未確認事項

テンプレートの定義を、そのまま実環境の現在値とみなさないでください。
また、情報が不足している状態で、実行可能な確定手順と断定しないでください。

【AWS公式資料から整理した前提】
以下を作業計画の確認観点として使ってください。

1. 構成
・2シャードでは、各シャードにプライマリが存在する。
・ReplicasPerNodeGroupは、クラスター全体ではなく各シャードのレプリカ数。
・追加後のノード数は、共有済みのレプリカ数を用いて計算する。
・レプリカ数に加えて、AZ配置、Multi-AZ、自動フェイルオーバーの状態を確認する。

2. バージョン
・ElastiCacheの指定値と、Redisのパッチ番号を含む表示を区別する。
・共有済みの更新先バージョンと、EngineVersionに指定する値を照合する。
・必要ならDescribeCacheEngineVersionsの結果を私に依頼する。

3. 更新時の影響
・エンジン更新時には既存クライアント接続が終了する。
・再接続、リトライ、指数バックオフ、クラスタートポロジー変更への追従を確認する。
・レプリカを追加しただけで無停止とは判断しない。
・CloudFormationの「No interruption」を、アプリの接続断や書き込み停止がない保証として扱わない。

4. CloudFormation
・ReplicasPerNodeGroupとNodeGroupConfigurationの指定方法を確認する。
・これらの併用や変更によるリソース置換の可能性に注意する。
・Change SetでAdd / Modify / Remove / Replacementを確認する。
・エンジン更新とパラメータグループ切り替えの組み合わせを確認する。
・CloudFormation経由での適用タイミングを確認し、CLIのApplyImmediatelyの仕様をそのまま当てはめない。
・CloudFormationの更新完了だけでは、アプリの正常動作まで確認できたことにはならない。

5. パラメータグループ
・Redis OSS 7系のファミリーはredis7。
・旧グループの設定を機械的に全転記しない。
・旧環境の独自設定と、新ファミリーのデフォルト・変更可能条件・反映時期を比較する。
・クラスターモード、maxmemory-policy、メモリ予約、タイムアウト、通知など、現場で使用している設定を確認する。
・削除・名称変更されたパラメータにも注意する。

6. 互換性
・使用しているクライアントライブラリ、Lua、ACL、Pub/Sub、コマンドを対象に確認する。
・Redis 7系にはSTRALGOからLCSへの変更、ACLや一部コマンドの戻り値の変更がある。
・使用していない機能まで網羅するのではなく、実際のアプリへの影響を評価する。

7. 復旧
・Redis OSS 7系から6系への直接ダウングレードを前提にしない。
・CloudFormationの自動ロールバックだけを復旧手段にしない。
・更新前の6系スナップショットから別の6系環境を復元し、接続先を切り替える案を検討する。
・実際の復元可否、所要時間、接続先変更、バックアップ取得後の書き込みの扱いを検証する。

【最初に分析してほしいこと】
共有済み情報を整理したうえで、既存CloudFormationと実環境を照合するために必要な情報を挙げてください。

主な確認対象：
・対象スタック、ネストされたスタック、リソースの論理IDと物理ID
・Engine / EngineVersion
・シャード数、各シャードのレプリカ数
・ReplicasPerNodeGroup / NodeGroupConfiguration
・ノードタイプ、AZ配置、Multi-AZ、自動フェイルオーバー
・サブネット、セキュリティグループ、暗号化、認証方式
・パラメータグループのファミリーと独自設定
・バックアップ設定
・Outputs、Export、共有リソースへの依存関係
・保留中の変更や更新状態
・テンプレートと実環境の差異

すべてを一度に要求せず、最初の判断に必要な情報から順に依頼してください。

【検証作業の基本案】
以下の順序が現行構成で適切か分析してください。

1. 既存CloudFormationから現行6系の検証環境を作成する。
2. 検証データを準備し、更新前のアプリ動作と性能を記録する。
3. 共有済みの数までレプリカを追加する。
4. ノードの正常性、同期状態、レプリケーション遅延、AZ配置を確認する。
5. 新しいパラメータグループを準備する。
6. エンジンと適用パラメータグループを更新する。
7. 更新中・更新後のアプリ動作、接続復旧、データ、性能を確認する。
8. 切り戻し手順と所要時間を検証する。
9. 本番に適用する手順、実施条件、中止・復旧判断を確定する。

検証環境の作成では、名前やExportの重複、本番への意図しない参照、接続先の取り違えを確認してください。
テンプレートのコピーと、Redis内のデータのコピーは別作業として整理してください。

【最終的に整理したい成果物】
情報がそろった段階で、チャット上に次を出力してください。

・現行／レプリカ追加後／バージョン更新後の構成比較表
・CloudFormationの変更箇所と変更理由
・旧／新パラメータグループの比較表
・検証手順と合格条件
・本番作業手順と各段階の確認事項
・中止条件、復旧判断、切り戻し手順
・保存する証跡の一覧

ファイルを直接変更できないため、必要なコード変更は対象箇所と差分として提示してください。
ただし、最初から完成版コードや大量の実行コマンドを出さず、現行構成の分析から始めてください。
